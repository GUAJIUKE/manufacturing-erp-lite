# 5–7 分钟面试演示脚本（Demo Script）

> 目标：一次讲清「这是什么系统、解决了什么、难点在哪」。
> 前置：seed_demo 已跑（确定性数据，见 README 快速开始 §1）。
> 配合 docs/screenshots/ 截图对照更佳。**只讲关键点，不念代码。**

---

## 准备（30 秒）

后端 8000 + 前端 5173 已启动，用 **admin** 登录进 Dashboard。

## 开场（30 秒）

> 「这是一个面向制造企业『采购申请 → 审批 → 采购订单 → 收货入库 → 库存』
> 协同场景的轻量 ERP Demo。前后端分离：Vue3 + TS + Element Plus 前端，
> FastAPI + SQLAlchemy + MySQL 后端。我今天重点演示它的**业务闭环**和几个
> 我认为设计上比较硬的地方：状态机、权限、并发与库存账。」

---

## 第 1 步：Dashboard（1 分钟）— admin

- **操作**：停留在数据看板，从上到下扫过。
- **展示**：6 张 KPI 卡（待审批 2 / 待转 2 / 待确认 PO 1 / 待收货 PO 1 /
  低库存 2 / 库存金额 ¥1,190.00），下方 PR 趋势、PO 状态分布。
- **讲**：所有 KPI 都是后端 SQL 聚合 + **按角色数据范围**算出来的。注意「待转
  采购 = 2」不是简单的"APPROVED 的 PR 数"——系统支持拆单，一张 PR 可能只转
  了一部分，所以口径是『APPROVED 且仍有明细没转完』。KPI 点进去能下钻到明细
  列表，**口径一致**是这里刻意做的（面试官若追问给 docs/dashboard_metrics.md）。

## 第 2 步：申请人创建并提交 PR（40 秒）— zhangsan

- **操作**：退出 → zhangsan 登录 → 采购申请 → 新建（选物料 ESP32 模组、
  数量 100、预估单价 10）→ 保存为草稿 → 提交。
- **展示**：DRAFT 态可自由编辑；提交后状态变 PENDING、内容冻结。
- **讲**：状态是服务端状态机管的白名单流转——前端按钮只是体验，真正拦截在
  Service 层；PENDING 之后任何编辑请求都会被拒（这点马上能在越权测试看到）。

## 第 3 步：主管审批（30 秒）— lisi

- **操作**：退出 → lisi 登录 → 审批中心 → 打开这张 PR → 填写意见 → 通过。
- **展示**：PR → APPROVED。
- **讲**：审批人不是"有 pr:approve 权限就能批"——Service 会查
  `department_managers`，**必须是这张 PR 申请部门的主管**（对象级权限）。
  换个部门主管来批会直接 403，后面如果时间允许可以演示。

## 第 4 步：采购员创建并确认 PO（40 秒）— wangwu

- **操作**：退出 → wangwu 登录 → 采购订单 → 从 PR 创建（选那张 APPROVED 的
  PR、订购 100、单价 10）→ 确认。
- **展示**：PO DRAFT → CONFIRMED；来源映射（sources）能看到"这张 PO 明细来自
  哪张 PR 明细、多少数量"。
- **讲**：转单是**数量链**：来源合计必须严格等于订购数量；PR 明细上的
  `converted_quantity` 用 CAS 更新，两个采购员同时转同一张 PR 不可能超转——
  第二个会收到"可转数量不足"。确认时强制单价 > 0。

## 第 5 步：仓库第一次收货（40 秒）— zhaoliu

- **操作**：退出 → zhaoliu 登录 → 采购入库 → 新建：选 PO、原材料仓、收 40 → 提交。
- **展示**：PO → PARTIALLY_RECEIVED；库存页出现 ESP32 40 件，单价 10、
  金额 ¥400。
- **讲**：一次收货在**一个事务**里同时写：入库单 + PO 已收量 + 库存流水 +
  库存余额 + PO 状态 + 审计——任何一步失败整体回滚。可以提：如果第二行超收，
  第一行也跟着回滚（这是多行入库单第二行超收的测试案例，docs/transaction.md）。

## 第 6 步：查看库存 Balance（20 秒）— zhaoliu

- **操作**：库存 → 当前库存。
- **展示**：ESP32 40 件；注意轴承行**低库存红标**（低于安全库存 50/15）。
- **讲**：余额是**快照**，流水是**账本**。这里能看到移动加权平均单价。
  提一个反直觉设计：冲销时不按"当前均价 × 数量"回滚，而是按**原始流水金额**
  回滚——保证 SUM(流水) == 余额永远成立。

## 第 7 步：第二次收货收满（30 秒）— zhaoliu

- **操作**：再建一张入库单，这次也直接演示**超收被拒**：先试着收 70
  （剩余 60）→ 系统拒绝并提示剩余可收 60 → 改成 60 → 提交。
- **展示**：PO → RECEIVED；库存 ESP32 = 100。
- **讲**：超收是被数据库**条件更新**拒的：`UPDATE ... WHERE received_quantity
  + 60 <= ordered_quantity`，rowcount=0 就拒绝。两个仓库员并发收货也只会成功
  一个——这就是 CAS，不是先 SELECT 再 UPDATE（那是会超收的错误写法）。

## 第 8 步：查看 signed ledger（20 秒）— zhaoliu

- **操作**：库存 → 库存流水。
- **展示**：+40 / +60 两条 PURCHASE_IN；每行有 txn_no、来源入库单号、
  balance_after 快照。
- **讲**：流水是 **append-only**：MySQL 触发器禁止对这张表 UPDATE/DELETE，
  应用层连这个念头都没有；错了就写一条负向流水纠正，原始记录永远在，
  这是审计与对账的地基。

## 第 9 步：冲销（40 秒）— zhaoliu

- **操作**：入库单列表 → 打开第二次收货的入库单 → 冲销 → 填原因 → 确认。
- **展示**：Receipt → REVERSED；流水多一条 `-60` 的 PURCHASE_IN_REVERSAL
  （指向原始流水）；库存回 40；**PO 状态从 RECEIVED 自动退回
  PARTIALLY_RECEIVED**。
- **讲**：两个点——(1) PO 状态不是硬编码"冲销了就是部分收货"，而是按明细
  数量**重新推导**的（recompute），所以冲销最后一笔会一路退回 CONFIRMED；
  (2) 并发冲销保护：状态翻转是原子 claim，两个人同时点冲销只有一个人成功。

## 第 10 步：回到 Dashboard 收尾（20 秒）— admin

- **操作**：退出 → admin 登录 → 数据看板 → 低库存行点下钻。
- **展示**：KPI 随上面操作实时变化；下钻列表带查询条件。
- **讲**：一句话收尾——「整个 Demo 我想强调的是：**业务闭环真实可跑，
  一致性不是靠前端约束，而是状态机 + 对象级权限 + 事务 + CAS + append-only
  账本在数据库和服务层兜底**。详细设计文档在仓库 docs/ 下，测试 229 项、
  覆盖率 91%。」

## 时间盒（总 5–7 分钟）

| 步骤 | 建议时长 | 可裁剪点 |
|---|---|---|
| 开场 + Dashboard | 1.5 min | 若超时：Dashboard 快速过 |
| PR 创建/提交 + 审批 | 1 min | 审批讲"对象级"一句带过 |
| PO 创建/确认 | 0.5 min | — |
| 两次收货 + 超收演示 | 1.5 min | 超收演示是亮点，别裁 |
| 流水 + 冲销 | 1.5 min | 冲销回退 PO 状态必讲 |
| 收尾 Dashboard | 0.5 min | — |

若面试官对某块特别感兴趣（并发/权限/事务），保留 docs/ 文档链接随时深挖。
